# Abhi's Dance Studio

Attendance & invoicing app. React (Vite) client + Express/Postgres server.

> This file is the source of truth for running the app locally and deploying it. It's reconstructed directly from the current project config (`docker-compose.yml`, `package.json`, `render.yaml`, etc.), so it stays accurate even if a previous conversation's notes get lost — keep it updated as the setup changes.

## Prerequisites

- Node.js
- Docker Desktop (runs the local Postgres database)
- Git (already set up in this folder — see `git log`)

## Run it locally

1. **Start the database**
   ```
   npm run db:up
   ```
   This starts a Postgres container (`docker-compose.yml`) on `localhost:5432`, database `abhi_dance_studio`, user `abhi` / password `abhi_dev_password`.

2. **Install dependencies** (once, or after pulling dependency changes)
   ```
   npm install
   ```
   This is an npm workspaces repo (`client` + `server`), so one install at the root covers both.

3. **Environment files** — already present for local dev (`.env` at root, `server/.env`), copied from `.env.example`. Not committed to git. If they're ever missing, recreate from `.env.example`:
   ```
   DATABASE_URL=postgres://abhi:abhi_dev_password@localhost:5432/abhi_dance_studio
   SESSION_SECRET=change-me-to-a-long-random-string
   PORT=4000
   NODE_ENV=development
   ```

4. **Run migrations**
   ```
   npm run migrate
   ```

5. **Start the app** (two terminals/processes)
   ```
   npm run dev:server   # Express API on http://localhost:4000
   npm run dev:client   # Vite dev server on http://localhost:5173
   ```
   Open **http://localhost:5173** — the client dev server proxies `/api` requests to the server on port 4000 (see `client/vite.config.js`).

6. **First run**: the app has no login yet — it'll prompt you to set a 4–6 digit PIN on first load (`POST /api/auth/setup`). That PIN is how you log back in afterward.

### Other useful scripts (run from repo root)

| Command | What it does |
|---|---|
| `npm run db:down` | Stop the local Postgres container |
| `npm test` | Full test suite (server API tests + client unit tests) — see below |
| `npm run backup` | Dumps all tables to a timestamped JSON file in `backups/` (gitignored — contains real student data) |
| `npm run restore` | Restores from a backup file |
| `npm run build` | Builds the client for production (`client/dist`) |

### Testing

```
npm test          # everything
npm run test:api  # server API tests only (spins up/migrates an isolated abhi_dance_studio_test DB first)
npm run test:unit # client unit tests only
```

Requires Docker running and `.env.test` at the repo root (gitignored) pointing at the isolated test database — see `.env.example` for the shape.

## Deploying to production

This repo is set up as a **Render Blueprint** (`render.yaml`) — it provisions a managed Postgres database and a Node web service together from one file.

1. **Push this repo to GitHub** (Render deploys from a connected git provider, not local files):
   ```
   git remote add origin <your-github-repo-url>
   git push -u origin master
   ```
   Create the empty GitHub repo first if you haven't (via github.com or `gh repo create`).

2. **In the Render dashboard**: New → Blueprint → connect the GitHub repo. Render reads `render.yaml` and provisions:
   - A free Postgres database (`abhi-dance-studio-db`)
   - A free Node web service (`abhi-dance-studio`) with:
     - Build: `npm install && npm run build` (installs deps, builds the client into `client/dist`)
     - Start: `npm run migrate && npm start` (runs migrations, then starts Express — which also serves the built client in production, per `server/index.js`)
   - `DATABASE_URL` is wired automatically from the provisioned database.
   - `SESSION_SECRET` is auto-generated by Render (`generateValue: true`).
   - `NODE_ENV=production` is set automatically.

3. **Deploy.** Render builds and starts the service; your first visit to the live URL will prompt for PIN setup again, same as local first-run (it's a fresh database).

4. **Subsequent deploys**: pushing to the connected branch on GitHub auto-deploys (Render's default), running the same build/start commands, including migrations.

No manual env var setup is required beyond what's in `render.yaml` — that's the point of the Blueprint. If you outgrow the free plan or add new env vars the app needs, edit `render.yaml` and redeploy.
